# FS25_SettingsHub Roadmap

Implementation roadmap for the settings bedrock. Newest entries at the bottom. Created 2026-10-05 under the office rule that every fix carries its ROADMAP.md and TODO.md lines in the same PR; earlier work is in the git history and the tracking repo's implementation roadmap.

## 2026-10-05 (Fred): enum options survive the float32 network paths (MAINTENANCE row 217)

- [x] A number that is not whole crosses the network as float32: the admin event (`SettingsHubAdminEvent`) and NetworkSync's sync frames both write it with `streamWriteFloat32`. A declared enum option such as 0.8, 0.15 or 0.08 therefore arrived as 0.800000011920929 and the exact enum check refused it with no log: in multiplayer a client admin's change never applied on the server, and a host admin's change never reached the clients. `SettingsHub:_snapNetworkValue` now gives such a value back as the declared option it stands for, only within float32 rounding of that option (2^-23 of its size), on the two network paths: `applyAdminChangeFromNetwork` (server) and `onReadState` (client). A value no option explains is still refused. Float, int and bool settings are unchanged, and StateLedger's save path was already exact (it writes numbers with `%.17g`).

## 2026-10-07 (Fred): the hub binds NetworkSync and StateLedger through the mission (MAINTENANCE row 241)

- [x] SettingsHub reached NetworkSync and StateLedger through the bare globals `g_networkSync` and `g_stateLedger`, which each mod writes into its own mod environment, so in a game both read nil inside the hub and it bound neither: a client admin's change applied on the server but never came back to the clients (the Sell Price Ratio arrows that did not step), no admin value persisted, and the Admin Control Registry's network action never bound. The hub and the registry now read the mission's handle first (`mission.networkSync`, `mission.stateLedger`), then the bare global, at all four sites, and each handle binds on its own. StateLedger's delivery at load skips a selfPersisted companion, as registration already did, so the hub's stored copy never overwrites a companion's own value. On a client the hub takes the server's value for every module but calls `onChange` only for a module that is not selfPersisted (the hub's own mirror contract, Desk's option A): the difficulty dials and the creative-world flag apply on clients, and the selfPersisted companions (SeasonalCropStress too, from its own MAINTENANCE row 257) keep their own sync. The broadcast leaves out a nil admin value, so no later setting is shifted. Found by Bob's trace of jamesw8439's report; design origin none.
